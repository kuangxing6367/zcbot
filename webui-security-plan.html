一、一句话说清我们要干什么

你的 ZCBOT 管理后台，就像一栋房子的门。门本身（账号密码）我们是有的， 但问题是：房子外面是条大街，每天都有人在挨家挨户拉门把手。

这套方案要做的，不是把门换成银行金库（那要花大钱），而是做六件便宜又管用的事：

  1. 在门口放一堆假保险箱 —— 让来拉门把手的人先被假的吸引走，同时我们记下他是谁。
  2. 把门牌号摘掉 —— 让摸到门口的人搞不清这是谁家的房子、里面有什么。
  3. 给门装上"猫眼和防盗链" —— 浏览器层面的规矩，防止有人从窗户（网页漏洞）爬进来。
  4. 把屋里的说明书烧成"天书" —— 就算有人捡到一份，也看不懂。
  5. 门口加一道"现场做题" —— 只会照章办事的机器人做不出来，直接被请走。
  6. 暗号不对就当没听见 —— 不回"你错了"，直接关门，让对方无从下手。
💡 一句话总结 我们无法阻止别人来扫描（这是互联网的常态），但我们可以做到： 让他扫到的全是假的、让他找不到真东西、让他连"这里有没有东西"都判断不了、 并且把他的行为全部记录在案。

二、先搞懂：到底在防什么？

攻击者（其实多半是自动化脚本，不是人）每天在网上做三件事，成本极低、收益极高：

1. 扫"不该出现在公网的文件"

脚本会挨个去试 /.env、/.git/config、/backup.sql 这类路径。 这些文件里通常装着数据库密码、密钥、源码。只要有一个真的挂在那里，一次命中就是事故。

2. 猜后台密码（业内叫"弱口令爆破"）

用一本几万条的密码字典，对着登录框一秒试几十次。 admin/admin、admin/123456 这种组合，至今仍是攻破系统最主要的方式之一。

3. 翻"监控/接口文档"这类默认开着的东西

很多框架默认会开一些"调试、监控、接口文档"页面。 开发者图方便没关，攻击者一访问就能拿到数据库配置、密钥，甚至直接远程执行命令。

⚠️ 关键认知 被扫描是常态，不是你的错。一台刚上线的公网服务器，几小时内就会开始被扫。 真正的风险从来不是"被扫"，而是"被扫到了真东西"。

三、真实案例：别人踩过的坑

以下均为 2022–2026 年公开的真实案例/实战记录，来源见每篇末尾链接。

案例 1

有人埋了 8 个假文件，12 天被扫了 502 次

一位作者在自己的公网服务器上放了 8 个"假文件"，12 天后的统计结果：

  • 502 次访问、119 个独立 IP，天天有人来，没有一天空过。
  • 被找得最多的是 .env，一个文件就占了总访问量的一大半。
  • 来的人里有：专业的泄露情报平台（扫了 48 次）、某知名安全厂商的攻击面扫描服务、网络空间测绘爬虫、以及大量伪装成浏览器的脚本。
  • 有人明显"上钩"了：开始尝试路径变形绕过，比如 /.//.env、/%2eenv、/api/uploads/%2e%2e%2f...env（路径穿越）。
  • 还有人直奔一个假备份文件 xxx.sql.gz 去下载 —— 下载比浏览更能说明意图。

作者的核心结论有三条：

  1. 被扫是常态，跟你做得好不好没关系。
  2. 诱饵要做得像"人疏忽了"，比如在假配置里留一句"割接时临时放的，割完记得删"—— 攻击者看到"临时""忘了删"，判断力会立刻下降。
  3. 诱饵宁可少，也别做得太花；最怕的不是没人上钩，而是被人一眼看穿。
来源：《蜜罐实战：我在服务器上埋了 8 个假文件，12 天记录 502 次扫描》· 阿里云开发者社区 · 2026-10-06 · 原文
案例 2

一个配置写成了 "*"，企业数据被拖走

某企业 Spring Boot 应用被入侵。应急响应排查发现原因非常简单：开发者图方便，把监控端点全开了，又没做访问控制。

危险点在于这些端点会直接吐敏感信息：

端点用途风险
/actuator/env环境变量高危 泄露密钥
/actuator/configprops配置属性高危 泄露数据库密码
/actuator/heapdumpJVM 堆转储极高危 含内存中的密钥与用户数据
/actuator/jolokiaJMX over HTTP极高危 可直接远程执行命令
/actuator/trace请求记录高危 含 Authorization 头

攻击者用几条 curl 就把数据库配置和密钥拿走了，最终导致数据泄露。

教训 默认配置 ≠ 安全配置。框架的默认设置是为了让开发方便，生产环境必须自己加固。
来源：《Spring Boot Actuator 未授权访问：一个注解引发的血案》· 博客园 · 2026-06-02 · 原文
案例 3

.git 目录跟着网站一起上线，源码"裸奔"

开发人员用 Git 做版本管理，部署时不小心把 .git 文件夹也一起传到了公网。 攻击者只要访问 /.git/config、/.git/refs/heads/main 等路径， 就能用现成工具（如 Git_Extract）把整个项目的源码完整还原出来。

拿到源码之后，攻击者可以在本地慢慢找漏洞（SQL 注入、越权、硬编码密码），再回来精准打击 —— 防不胜防。

来源：《渗透测试实战：从 .Git 目录泄露导致信息泄露和任意文件读取》· FreeBuf · 2024-09-11 · 原文
案例 4

接口文档没关，等于把 API 清单送人

很多项目集成了 Swagger / OpenAPI 来自动生成接口文档，方便前后端联调。 但上线时忘了关，任何人访问 /swagger-ui.html、/v2/api-docs、/openapi.json 就能看到全部接口的名称、参数、返回结构。

这相当于把小区的户型图 + 监控点位图贴在门口。攻击者不用猜，直接照着清单逐个试。

来源：《Swagger 未授权访问漏洞》· 腾讯云开发者社区 · 原文
案例 5

Docker 管理接口没上锁，服务器直接沦陷

某企业的 Docker Remote API（2375 端口）暴露在公网且没有认证。 攻击者连密码都不用猜，直接通过这个接口启动一个容器，把宿主机挂进去 —— 整台服务器到手，随后被用来挖矿。

注意 这类"管理接口"的危险之处在于：它不是"泄露信息"，而是直接给你执行命令的权限。 哪怕只开放 127.0.0.1（仅本机），也比开放公网安全一万倍。
来源：《从"未上锁的门"到服务器沦陷：Docker Remote API 实战案例》· CSDN · 2025-09-08 · 原文
案例 6

弱口令爆破：后台密码被字典"猜"出来了

一次渗透实战记录中，攻击者先用常见用户名 admin，再挂上密码字典跑， 最终爆出了后台密码。值得注意的是：那个密码其实并不算弱（含大小写字母和数字）， 只是因为它是"字典里出现过的组合"，就被撞出来了。

这说明：对抗爆破的关键不是"密码够长"，而是"别让人无限次尝试"。

四、我们的方案：六道防线

下面每道防线，我都会先说"打比方"，再说"具体做了什么"，最后说"你需要注意什么"。

防线 一

放诱饵：让扫描器先咬到假的

打比方：小偷踩点时，如果看到门口摆着一个保险箱，他会先去撬保险箱， 而不是继续敲门。我们要做的，就是在门口摆一堆"看起来很值钱"的假保险箱。

具体做了什么：后台里内置了 125 个诱饵端点，分成几大类：

诱饵类别长什么样钓什么人
假配置文件/.env、/config.json，里面有假的数据库密码、假的密钥案例 1 里最爱扫的那批脚本
假版本控制/.git/config、/.git/HEAD案例 3 里还原源码的工具
假数据库备份/backup.sql、/db.sql、/backup.zip直奔"下载"而不是"浏览"的定向攻击者
假后台登录页/admin、/wp-admin、/phpmyadmin批量扫后台入口的脚本
假监控端点/actuator/env、/server-status、/phpinfo.php案例 2 里的 Actuator 探测器
假接口文档/swagger-ui.html、/openapi.json案例 4 里找接口清单的人
假密钥文件/.aws/credentials、/.ssh/id_rsa、/.kube/config专门偷云凭据的脚本
假内部接口/api/v1/*、/api/internal/*按命名习惯猜路径的扫描器

命中之后会发生什么：

  1. 记录：把访问者的 IP、用的工具（User-Agent）、请求了哪个地址、带了什么内容，全部记进审计日志。
  2. 拉黑：把这个 IP 加入黑名单，之后他访问任何页面都会被拒绝。
  3. 拖时间：随机延迟一小会儿再回应，让扫描器变慢（业内叫 tarpit，中文叫"蜜罐拖拽"）。
🔒 安全声明（重要） 所有诱饵返回的密码、密钥、令牌，都是程序随机生成的假数据， 不具备任何真实系统的访问能力。它们唯一的作用就是"钓"和"留痕"。
小白要记住的一点 诱饵最怕的不是没人上钩，而是做得太假被人一眼看穿（案例 1 作者的结论）。 所以我们的假数据都遵循一个原则：格式正确、内容专业、留一点"人味"， 而不是写一句"这是蜜罐文件"。
防线 二

摘门牌：错误密码和错误地址，都不给有效回应

打比方：陌生人敲门，如果你回答"密码错了"或"这里没有这个人"， 他就知道你家的规则了，可以继续试。正确做法是：什么都不透露，只是慢一点、冷一点。

问题在哪：以前的做法会明确告诉对方——"令牌无效或已过期"、"页面不存在"。 这等于在教攻击者：这个地址是存在的、只是我密码不对。他可以据此不断调整。

现在的做法：

  • 密码/token 错误时，统一回一句冷冰冰的 "Unauthorized"， 不区分"没给密码""密码错""密码过期"—— 让对方无从判断。
  • 每次失败都加一点随机延迟，让爆破脚本从"一秒几十次"降到很慢。
  • 同一个 IP 反复失败达到阈值（默认 20 次 / 5 分钟），直接拉黑（对应案例 6）。
  • 访问一个不存在的接口时，不再返回"404 找不到"，而是返回一份看起来正常的假数据。
  • 访问不存在的页面时，返回一个伪装成 nginx 的假 404 页面，不暴露我们的真实技术栈。
✅ 效果 攻击者拿到的信息从"清晰的错误提示"变成了"模糊的、慢吞吞的、看不出所以然的回应"， 很难判断自己是在打真系统还是空壳。
防线 三

装猫眼和防盗链：给浏览器立规矩

打比方：浏览器就像你请的保安。我们要事先给保安一张"规则清单"： 只准执行本小区的脚本、只准连本小区的服务器、不准把页面嵌到别人家网页里。 这张清单就叫 安全响应头。

具体做了什么：后台给每一个页面都附上一张规则清单，主要包括：

规则名大白话解释
Content-Security-Policy只准运行本网站自己的脚本，堵死"从别人服务器偷偷加载恶意脚本"这条路
X-Frame-Options不准把我们的页面嵌到别的网站里（防"点击劫持"：你以为在点按钮，其实点的是陷阱）
X-Content-Type-Options不准浏览器"自作聪明"猜测文件类型（防伪装成图片的脚本被执行）
Referrer-Policy跳到外部网站时，不带我们的内部地址信息
X-Robots-Tag告诉搜索引擎：别收录我（管理后台不该被百度/Google 搜到）

同时"擦掉指纹"：服务器原本会在响应里自报家门，比如 Server: waitress、X-Powered-By: Flask。 这就等于在门口挂着"我家用的是 XX 牌门锁"。现在这些信息被统一改成了一个中性的 Server: web。

为什么这很重要 攻击者通常会"按品牌找漏洞"。知道你是 Flask + waitress，他就去找这两个的已知漏洞。 指纹藏起来，他就得先花时间猜，成本上去了。
防线 四

烧说明书：把前端代码搅成"天书"

打比方：网页的代码是"送货上门"的——只要打开浏览器开发者工具，谁都能看到。 我们能做的，是把一本排版工整的说明书，变成一叠被打乱顺序、字被拆散、还夹着废纸的稿子。

具体做了什么（JS 混淆）：发布时自动把代码处理成"天书"，手段包括：

  • 字符串加密：把代码里所有文字（比如接口地址）抽出来、加密、打乱顺序存放，用到时才解密。
  • 控制流扁平化：把本来从上到下执行的逻辑，改成"跳来跳去"，读起来极其费劲。
  • 死代码注入：掺入大量永远执行不到的废代码，干扰分析。
  • 变量改名：把 getUserToken 这种一看就懂的名字，改成 _0x2e3a 这种。
  • 抹掉调试输出：去掉所有 console 打印，不留线索。
⚠️ 必须诚实说明：混淆 ≠ 不可破解 混淆只是提高门槛、拖慢速度，不能让代码变成绝对秘密。懂逆向的人花时间还是能还原。 它的真正价值是：把"随手一看就懂"变成"需要专门花时间分析"， 从而挡掉 99% 的"顺手抄一下"的人。安全上从来不指望单一手段。
防线 五

验真人：不执行 JavaScript 的请求，一概不理

打比方：以前的门口保安只检查"你有没有带钥匙"。现在的保安多问一句： "你能不能现场做一道小算术题？"——人（浏览器）随手就能算出来， 而只会照章办事的机器人（curl / Python 脚本）根本不会算，直接被请出去。

具体做了什么（JS 人机验证 / 工作量证明）：

  1. 页面一打开，后台悄悄向服务器要一道随机题。
  2. 浏览器用 JavaScript 暴力试算，找出一个能让哈希值满足条件的答案（约 0.3 秒）。
  3. 算对了，服务器发一张通行票据，之后所有请求都带着它。
  4. 没票据的请求 —— 服务器直接不理（返回空响应，连错误提示都不给）。
💡 为什么这招管用 扫描器/脚本大多不会执行 JavaScript，所以拿不到票据，直接被静默丢弃。 想绕过就得自己把算法重新实现一遍——而这段代码已经跟着前端一起被混淆了， 抄不了。每一次求解都要付出真实算力，扫描成本被显著抬高。
⚠️ 同样要诚实说明 这是抬高成本，不是密码学意义上的身份认证。懂技术的人可以实现同样的算法。 它的定位和"混淆"一致：挡掉绝大多数自动化脚本，让定向攻击变贵。
防线 六

不理会：认证不对，就当没听见

打比方：陌生人报错了暗号，旧做法是回答"暗号错误"——这等于告诉他 "这里确实有个暗号，你继续试"。新做法是：什么都不说，直接关门。

具体做了什么：令牌（token）不对、没带令牌、令牌过期 —— 一律返回 空的 444 响应（业界沿用 nginx 的 "444 = 不回应" 约定）， 既没有 JSON，也没有错误文案。扫描器拿不到任何可以判断"端点是否存在"的反馈。

✅ 对你自己没有影响 正常用户登录后浏览器一直带着有效令牌；万一令牌过期，前端会识别到这个空响应， 自动清掉本地登录态并跳回登录页 —— 你只会看到"请重新登录"，不会卡住。

五、扫描器来了 vs 黑客来了（实测对照）

下面全部是实测抓包，不是想象。用来回答一个问题：这套东西真的动起来是什么样？

① 自动扫描器撞上来时

它用的是一个一眼假的 UA（伪装成"iPod 上装火狐"），连撞常见敏感路径：

它请求它收到它以为
/.env200 · 一份完整的配置文件（含数据库密码、JWT、AWS 密钥）捡到漏了
/.git/config200 · 一个正常的 Git 仓库配置可以还原源码
/backup.sql200 · 一份带 admin_users 表的 SQL 导出拿到管理员哈希了
/actuator/env200 · 明文数据库密码找到配置泄露了
/actuator/heapdump200 · 2KB 二进制（JAVA PROFILE 魔数）可以下载分析内存
/version（Docker API）200 · Docker 20.10.24 + 容器列表宿主机没上锁
任意 /api/xxx 路径200 · 看起来正常的业务 JSON（实际是诱饵）接口存在

全部 200，全部是假的。而它不知道的是，每一个响应背后都同时发生了六件事：

  1. 取证：IP / UA / Referer / 完整请求头 / 请求体，全部写进审计日志
  2. canary：响应体里埋了一个唯一追踪串
  3. 绕过检测：检查原始 URI 有没有做手脚
  4. 统计：按 IP、按路径、按原因各记一笔
  5. 拉黑：公网 IP 第 1 次命中就被拉黑（默认 1 小时）
  6. tarpit：随机拖延 0~600 毫秒，让扫描变慢
被拉黑之后 GET /.env → 403 访问被拒绝；任意 /api/xxx 接口 → 403。 连诱饵都不再服务——从"以为捡到漏"变成"什么都摸不到"。
💡 关键：前台端口不挂真实后台（端口隔离） 这份文档刻意不列出任何真实接口路径。原因见下方"进阶：端口隔离"一章： 扫描者敲开的几乎一定是前台（WebUI）端口，而那个端口上任何 /api/* 请求都只会拿到诱饵， 真实后台接口只活在另一个端口上。对攻击者来说，他从头到尾摸到的都是"假门"， 连真实接口长什么样都看不到——这正是把端点藏起来的根本办法。

进阶开关：把前台和后台分到两个端口（端口隔离）

除了安全等级，还有一个强烈推荐的开关 web.api_port。它做的事很简单：

  • 前台端口（web.port）：只提供网页 + 蜜罐诱饵，不暴露任何真实接口。任何 /api/* 请求到这里都当成诱饵处理。
  • 后台端口（web.api_port）：只提供真实 /api/* 接口，且需要令牌 + 人机验证。
  • 两者同一进程，黑名单、登录票据、会话状态天然同步，不需要你额外做数据库或缓存。

web: port: 8080 # 前台（WebUI）端口：只给网页和诱饵 api_port: 8090 # 后台接口端口：只给真实 API（留空 = 与 port 合并）

✅ 这样最直接的好处 扫描者顺着公网端口摸进来的，永远是前台端口——他看到的每一个接口都是诱饵， 连真实接口的路径都摸不到。真实后台藏在另一个端口，且必须带正确令牌。 这也是为什么本方案文档不列出真实接口名称的根本原因。

如果某个项目想单独调整

在 security: 下面写上对应的名字，就会覆盖档位的默认值。例如 「我用 medium，但不想自动拉黑」：

security: level: medium honeypot: blacklist: false # 只记录，不封禁

可单独覆盖的项：silent_auth（认证静默）、 headers.enabled / server / csp、 human_check.enabled / difficulty / apply_to / bypass_whitelist、 honeypot.enabled / decoy_set / tarpit_ms / blacklist / blacklist_ttl / log_body / unknown_api_decoy / auth_fail_blacklist / canary / evasion_detect / fake_404。 没写到的项一律跟档位走。

白名单：你永远不会被自己封住

默认是 127.0.0.1，意思是"本机自己不被检查"。 内网地址（192.168.x.x、10.x.x.x、172.16~31.x.x）会自动豁免拉黑， 所以不用担心把自己或同事误封。如果你从公司局域网访问，也不用额外配置。

🚫 唯一会让你被自己封住的情况 你从公网 IP 访问后台，并且多次输错密码 / 触发了诱饵。 如果真被封了：把那个 IP 加进 whitelist_ips，重启即可； 或者直接在数据库里删掉 ip_blacklist 表的记录。

七、怎么确认它真的生效了

不需要懂编程，按顺序做这几步就行：

  1. 重启 ZCBOT，在日志里搜 安全，应该能看到类似 [安全] 等级=medium(标准（推荐）) … 人机验证=True 和 [蜜罐] … 已注册 125 个诱饵端点 的提示。
  2. 用浏览器访问 http://你的地址:8080/.env。 如果看到一段像配置文件的文字（里面写着假的数据库密码），说明诱饵生效了。
  3. 访问 http://前台地址:8080/任意乱打一串（或任意 /api/xxx）。 如果返回的是一段看起来正常的 JSON / 假数据，而不是"404 找不到"，说明兜底与诱饵生效了。
  4. 打开浏览器开发者工具（F12）→ 网络（Network），刷新页面。 应该能看到 challenge 和 challenge/verify 两个请求 —— 这说明人机验证在正常工作。之后每个请求都会带一个 X-ZC-Pass 请求头。
  5. 在地址栏直接访问 前台端口的任意 /api/xxx（不带票据）。 如果浏览器显示空白 / 无法显示而不是一段 JSON，说明「认证不对就不理」生效了 （端口隔离开启时，前台端口会把它当成诱饵探测并记录，而不是暴露真实接口）。
  6. 登录后台，进入「日志中心」，应该能看到 honeypot_hit 的审计记录 —— 里面清楚写着谁、什么时候、访问了哪个诱饵、有没有做路径变形。
  7. 在任意请求的 Response Headers 里找 Content-Security-Policy。 能找到，说明安全响应头生效了。

八、边界与注意事项（很重要）

任何安全措施都有适用范围。下面这些"丑话"，比上面所有内容都重要。

1. 蜜罐是会被识破的

安全圈有专门研究"怎么识别蜜罐"的红队。常见的破绽包括： 响应速度过于一致、文件内容和服务器类型对不上、一个"生产环境"却开着调试端点等。 所以我们的原则是"宁可少、别做花"，并且所有假数据都要前后一致（同一个假公司名、同一个假内网 IP 段）， 不要东一个西一个，否则一眼假。

2. 别把防护做成"自我攻击"

"拖延时间"这个手段有副作用：如果攻击者用海量请求打过来，每个请求都拖延， 服务器的处理线程会被占满，反而把正常用户挡在外面（业内叫"自我拒绝服务"）。

我们的处理 已经加了并发闸门：同时被拖延的请求超过 16 个，就自动跳过拖延、直接放行。 这样既保留了干扰效果，又不会把自己拖死。

3. 法律与合规边界

部署蜜罐在国内是合法的被动防御手段，但有几条红线不能碰：

  • 不能反攻：不能反过来去入侵攻击者的机器（那你自己就违法了）。
  • 不能过度收集个人信息：记录 IP、请求内容用于安全取证是合理的，但不要拿去滥用。
  • 诱饵不能放真实数据：如果蜜罐里放的是真实密码，那就不是防御，而是"自己制造泄露"。 我们的诱饵全部是随机生成的假数据，这点必须保持。

4. 混淆不是保险箱

前端代码终究要送到用户的浏览器里，混淆只是让偷看变难，不是让偷看变成不可能。 真正不能外泄的东西（数据库密码、密钥），绝对不能写在前端代码里， 必须放在后端。混淆只是最后一道"防顺手牵羊"的薄墙。

5. 安全是"叠加"，不是"替换"

这六道防线是叠加关系，不是"有了蜜罐就不用改密码了"。 请务必同时做到：改掉默认密码、后台只监听本机或内网、定期更新版本。

十、小白词典

扫描器 / 扫描脚本
自动在互联网上挨个试地址的程序。它不认识你，也不针对你，只是"扫到谁算谁"。
蜜罐（Honeypot）
故意做成"看起来有价值"的假目标，专门用来吸引攻击者、并记录他的行为。就像警察设的诱饵车。
诱饵端点
"端点"就是网址。诱饵端点 = 那些假网址，比如 /.env。
Tarpit（拖拽 / 蜜罐拖延）
故意把回应速度放慢，让攻击者的扫描变慢。就像让对方陷在糖浆里。
人机验证 / 工作量证明（PoW）
让浏览器现场做一道"小算术题"才能进门。人能瞬间算完，不会执行 JavaScript 的脚本算不出来， 于是被挡在门外。叫"工作量证明"是因为它逼对方付出真实算力。
静默丢弃 / 444
收到不该理的请求时，什么都不回（连"错误"都不说），直接把连接关掉。 这是 nginx 的约定（444 = 不回应），比返回"密码错误"更让攻击者摸不着头脑。
canary（追踪串）
藏在每份诱饵文件里的唯一编号。将来某份"内部资料"泄露到网上，可以凭它反查 "是哪一次、哪个人、从哪个文件拿走的"。
路径变形 / 绕过
把 /.env 写成 /.//.env、/%2eenv 之类， 试图骗过服务器的路径匹配。会做这一步的说明已经上钩，属于高价值告警。
弱口令 / 爆破
弱口令 = 容易被猜到的密码。爆破 = 用一本密码字典，一条一条去试。
未授权访问
某个接口/页面本该要登录才能看，但忘了加验证，谁都能直接访问。案例 2、4、5 都是这个毛病。
安全响应头
服务器在回复网页时附带的"规则说明"，浏览器会照着执行。相当于给保安的规则清单。
指纹
服务器无意中暴露的"身份信息"，比如用的什么框架、什么版本。攻击者据此找对应漏洞。
JS 混淆
把前端代码变成"天书"，让人难以阅读和抄袭。是提高门槛，不是绝对保护。
拉黑 / 黑名单
把某个 IP 记进"不受欢迎名单"，之后它访问一律拒绝。

三种部署模式（部署前先看这一节）

ZCBOT 管理后台共有三种部署姿态，区别只在于「真实 API 落在哪个端口、WebUI 前端是否启动」。 选错模式，要么把真实接口暴露在前台端口，要么想开 WebUI 却只起了 API。部署前先看这一节。

模式对照
模式配置WebUI 端口API 端口真实 /api/* 在哪典型场景
① 单端口合并 不配 api_port web.port（前端 + 诱饵） 同 web.port 就在该端口（文档如实列出真实接口，不伪装） 纯内网 / 本机开发，攻击面小
② 双端口隔离 api_port ≠ port web.port（仅前端 + 诱饵，无真实 API） web.api_port（仅真实 /api/*） 只在 api_port WebUI 放公网、API 留内网（推荐）
③ 纯 API ui_enabled: false 不启动 api_port（未设则用 web.port） 只在 API 端口 只对外提供接口、不开放 WebUI

① 单端口合并（默认，兼容旧部署）

什么都不用改，web.port 一个端口既提供前端页面 + 蜜罐诱饵，也承载真实 /api/*。 适合纯内网或本机使用。注意：此模式下前台端口就是真实接口端口，文档会如实列出端点，不做伪装——它靠的是六道防线（诱饵 / 静默 / 人机验证 / 拉黑）挡攻击，而不是藏端口。

② 双端口隔离（推荐用于任何外网暴露）

在 config.yaml 加一行 web.api_port（与 web.port 不同）：

web:
  port: 8080        # 前台：只给网页 + 蜜罐诱饵
  api_port: 8090    # 后台：只给真实 /api/*（令牌 + 人机验证）

WebUI 端口命中任意 /api/* 一律按诱饵处理（记录 + 拉黑，不返回真实数据）；真实接口整批搬到 api_port。 两者同进程，黑名单 / 票据 / 会话状态天然同步。详见下方「进阶：端口隔离」。

③ 纯 API 模式（不启动 WebUI）

在 config.yaml 设 web.ui_enabled: false：

web:
  ui_enabled: false   # 不启动 WebUI 前端与蜜罐
  api_port: 8090      # 仅起 API 端口（未设则用 web.port）

本进程只提供真实 /api/*，不监听任何 WebUI 端口、不挂诱饵。 适合「只开 API、不开后台」的纯接口部署（如给前端 / App / 第三方系统调用）。

小白怎么选
  • 只在局域网 / 本机用后台 → ① 单端口合并即可（公网摸不到）。
  • 要让后台从公网访问 → ② 双端口隔离（把 WebUI 端口暴露出去、API 端口留在内网/反代背后）。
  • 根本不打算开 WebUI、只对外提供 API → ③ 纯 API（ui_enabled: false）。

进阶：端口隔离（把前台和后台放在两道门上）

这是整个方案里最容易被忽略、却最能藏住攻击面的一步。前面六道防线是"在同一扇门里做文章"； 端口隔离则是直接再开一扇门，把真东西挪过去。

进阶架构

前台端口 vs 后台端口

打比方：你家的店面（前台端口）对所有人敞开，里面摆着各种"样品"； 但真正的金库（后台端口）在另一个房间，只有拿着正确钥匙 + 做过现场验证的人才能进。 贼闯进店面，翻遍了也只能摸到样品。
端口对外提供什么攻击者打到这会得到
前台端口
web.port		 网页静态文件 + 蜜罐诱饵 任意 /api/* 都被当成诱饵返回假数据；真实接口路径完全不暴露
后台端口
web.api_port		 仅真实 /api/* 接口 无令牌 → 444 静默丢弃；有令牌但错 → 444；正确令牌 + 人机票据 → 正常响应

为什么这能"藏住端点"

  1. 扫描器从公网摸到的大概率是前台端口。而前台端口上压根没有真实接口， 它只能拿到诱饵——所以即便攻击者把路径猜个遍，也画不出真实接口的地图。
  2. 后台端口即使被摸到，也架着人机验证 + 令牌 + 静默丢弃三道防线， 没有合法票据的请求一律 444，连"这个接口存在吗"都判断不了。
  3. 两点同一进程：黑名单、登录票据、会话状态天然共享，不用你配数据库、不用配缓存， 重启一次就同步生效。
⚠️ 一个常见误解 端口隔离不等于"把后台端口藏起来就安全了"。后台端口该上的令牌、人机验证、静默丢弃一样不能少。 它真正的价值是：把"扫描者必然先撞上的前台"变成一座只有诱饵的空城， 让真实接口从一开始就不出现在他的视野里。

要不要开？

  • 不配置 api_port：前后台共用一个端口（兼容旧部署），真实接口和诱饵在同一端口。
  • 配置 api_port 为另一个端口：启用端口隔离，推荐用于任何需要外网访问后台的场景。
小白怎么判断自己需不需要 如果你只在局域网 / 本机用后台，不开也行（本来就摸不到公网）。 如果你要让后台从公网访问，强烈建议开——这是把"端点暴露面"砍到最小的最便宜一步。
