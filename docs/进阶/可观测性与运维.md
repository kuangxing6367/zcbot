# 可观测性与运维接口

框架自带三个只读端点，供容器探针、负载均衡和 Prometheus 使用。它们不依赖任何第三方库，也不需要登录。

| 端点 | 用途 | 是否需要鉴权 | 端口 |
|---|---|---|---|
| `GET /healthz` | 存活探针：进程能响应即 200，**不查数据库** | 否 | 任意端口 |
| `GET /readyz` | 就绪探针：进程运行中 + 启动完成 + 数据库可读 | 否 | 任意端口 |
| `GET /metrics` | Prometheus 文本格式指标 | 默认否，可配令牌 | 仅 API 端口 |

三个端点都不计入限速、不触发人机验证、不写审计日志——否则探针会自己把自己拦掉，或者把审计表刷满。

## 配置

```yaml
observability:
  health: true          # /healthz 与 /readyz
  metrics: true         # /metrics
  metrics_token: ""     # 非空时 /metrics 需要 Authorization: Bearer <token>
```

这三项在启动时读取，修改后需要重启（[配置热应用](#配置热应用) 里标注为需重启的段）。

若不想暴露指标端点，把 `metrics: false`：此时 `/metrics` 会交给蜜罐的诱饵（返回伪 actuator 内容，扫描器拿不到真实数据）。

## /healthz

```json
{"status": "ok", "uptime_seconds": 128.412, "version": "1.12.0"}
```

只反映「进程没死」。**故意不碰数据库**：探针把慢库拖成雪崩是常见事故，数据库健康交给 `/readyz`。

## /readyz

就绪时返回 200；任一必需检查失败返回 **503**，响应体带逐项明细，排障时直接看是哪一环没起来：

```json
{
  "status": "not_ready",
  "uptime_seconds": 3.21,
  "version": "1.12.0",
  "checks": {
    "process":  {"ok": true,  "detail": "运行中"},
    "startup":  {"ok": false, "detail": "插件加载中"},
    "database": {"ok": true,  "detail": "0.4ms"},
    "plugins":  {"ok": true,  "required": false,
                 "detail": "已加载 6，失败 0", "loaded": 6, "failed": 0}
  }
}
```

判定规则：

- `process`：框架处于运行状态（`start()` 之后、`stop()` 之前）；
- `startup`：插件加载完成。用 `startup.wait_ready: false` 异步启动时，加载完成前这里就是 `false`；
- `database`：执行一次 `SELECT 1`；写缓冲降级时仍算可用，但在 `detail` 里注明；
- `plugins`：只做信息展示（`required: false`），加载失败数量在这里暴露出来，不影响就绪判定——框架本身仍可服务。

## /metrics

Prometheus 文本格式（exposition v0.0.4），手写输出，不引入 `prometheus_client`。

| 指标 | 类型 | 说明 |
|---|---|---|
| `zcbot_up` | gauge | 恒为 1（进程能响应抓取） |
| `zcbot_build_info{version,python,storage}` | gauge | 版本 / Python / 存储类型，值恒为 1 |
| `zcbot_uptime_seconds` | gauge | 运行时长 |
| `zcbot_ready` | gauge | 就绪标记（与 `/readyz` 同一套判定） |
| `zcbot_plugins_loaded` / `zcbot_plugins_failed` | gauge | 已加载 / 加载失败插件数 |
| `zcbot_db_up` | gauge | 数据库可读 |
| `zcbot_event_buffer_items{layer}` | gauge | 事件缓冲各层待处理条目（l1 / l2_pending / l3 / l4） |
| `zcbot_event_buffer_bytes{layer}` | gauge | 各层占用字节 |
| `zcbot_event_buffer_dropped_total` | counter | 累计丢弃事件数 |
| `zcbot_ws_connections` | gauge | 已连接接入端数量 |
| `zcbot_process_resident_memory_bytes` | gauge | 进程 RSS（缺 psutil 时不输出） |
| `zcbot_process_threads` | gauge | 线程数 |
| `zcbot_http_requests_total{method,status}` | counter | HTTP 累计请求数（不含探针自身） |

`zcbot_http_requests_total` 只按「方法 + 状态码」打标签，不带 URL——避免任意路径把时序库基数打爆。

### 抓取配置

同机抓取（未设令牌）：

```yaml
scrape_configs:
  - job_name: zcbot
    static_configs:
      - targets: ["127.0.0.1:8080"]
```

跨机抓取建议设置令牌：

```yaml
observability:
  metrics_token: "换成一串随机字符"
```

```yaml
scrape_configs:
  - job_name: zcbot
    authorization:
      type: Bearer
      credentials: "换成一串随机字符"
    static_configs:
      - targets: ["10.0.0.5:8080"]
```

也支持 `?token=xxx` 查询参数，方便临时用 curl 排查：

```bash
curl -s "http://127.0.0.1:8080/metrics?token=xxx" | head
```

### 端口隔离时的可见性

开启 `web.api_port`（WebUI 与 API 分端口）后：

- `/healthz`、`/readyz`：两个端口都可用（编排系统不知道你的端口划分）；
- `/metrics`：只在 API 端口给出真实指标；WebUI 端口按「不暴露真实 API」的规则交给诱饵。

纯 API 模式（`web.ui_enabled: false`）下三个端点都可用。

## 后台「运行状态」页

不想 curl 的时候，后台 **运行状态** 页读的是同一份数据（`GET /api/runtime/stats` 新增
`health`、`event_buffer`、`requests`、`db_degraded` 四个字段，原有字段不变）：

| 区块 | 内容 |
|---|---|
| 健康检查 | 与 `/readyz` 的 `checks` 完全同构：进程 / 启动 / 数据库 / 插件逐项状态与详情，右上角就绪标记 |
| 事件缓冲 | L1 内存 / L2 待刷 / L3 缓冲 / L4 落盘 四层的条目数与占用（KB），以及累计丢弃数 |
| HTTP 请求分布 | 按 `方法 + 状态码` 聚合的 Top 10 累计次数 |

页面每 5 秒轮询一次。三处（`/readyz`、`/metrics`、运行状态页）在代码里共用
`framework/api/observability.py` 的同一批函数，若发现展示口径不一致，那是 bug 而不是设计。

> 注意：该页面走正常后台鉴权。若 `security.silent_auth: true` 且开启了双请求防破解认证，
> 用脚本直接 `curl` 登录接口会被静默丢弃（444），这是主动防御而非故障。

## 容器与 systemd 示例

Docker：

```yaml
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8080/healthz', timeout=3).status==200 else 1)"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 40s
```

Kubernetes：

```yaml
livenessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 20
readinessProbe:
  httpGet: {path: /readyz, port: 8080}
  periodSeconds: 10
  failureThreshold: 3
```

systemd 只在就绪后标记服务可用：

```ini
[Service]
ExecStartPost=/bin/sh -c 'until curl -sf http://127.0.0.1:8080/readyz >/dev/null; do sleep 1; done'
```

## 配置热应用

`PUT /api/config/yaml/<section>` 写盘后会把新值应用到运行中的框架，并在响应的 `msg` / `data` 里说明哪些字段已经即时生效、哪些仍需重启：

```json
{
  "code": 0,
  "msg": "配置段 [log] 已保存，日志级别即时生效: DEBUG",
  "data": {
    "section": "log",
    "live": true,
    "restart_required": false,
    "restart_reason": "",
    "notes": ["日志级别即时生效: DEBUG"]
  }
}
```

| 配置段 | 是否即时生效 | 说明 |
|---|---|---|
| `log` | 即时 | 日志级别直接改 root logger |
| `framework.blackbox` | 即时 | 黑匣子的开关与内存上限 |
| `security.rate_limit` | 即时 | 重建限速器；`honeypot` / `human_check` 仍需重启 |
| `plugin.hot_reload` | 即时 | 心跳读取最新值；`heartbeat_interval` 仍需重启 |
| `database` / `web` / `onebot` / `ssl` / `event_queue` / `dual_process` / `iipc` / `console` / `observability` | 需重启 | 连接、监听端口、证书、队列在启动时创建 |
| 其它（插件自定义段等） | 需重启 | 未注册即时应用能力的段一律保守判定 |

插件若想在配置变更时做自己的热应用，可注册 applier：

```python
from framework import hotapply

def _apply(framework, section_cfg):
    # section_cfg 是合并后的完整配置段
    return ['我的字段已即时生效']      # 返回已生效的说明，会回显给前端

hotapply.register('my_plugin_section', _apply)
```

## API 版本前缀

所有真实 `/api/*` 端点同时挂在 `/api/v1/*` 下，行为完全一致：

```bash
curl http://127.0.0.1:8080/api/version      # 旧路径，继续可用
curl http://127.0.0.1:8080/api/v1/version   # 版本化路径
```

- 旧路径不会移除，插件与脚本无需改动；
- 蜜罐兜底（`/api/<path>` 诱饵）不会被复制到 v1 下；
- 未来若出现破坏性变更，将在 `/api/v2/*` 提供新语义，`v1` 保持旧语义。
