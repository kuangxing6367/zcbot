# 数据库迁移

框架的表结构变更走**版本化迁移**：每个库有一张账本表 `schema_migrations`，记录「这个库已经应用到第几版、每版是什么时候、跑成功没有、当时的校验和是多少」。启动时只执行账本里没有的版本。

这套机制对齐主流迁移工具（Flyway / Liquibase / Alembic / Rails）的公共契约，不是自创约定：

| 契约 | 含义 | 本框架的落点 |
| --- | --- | --- |
| 账本表 | 版本状态存在库里，不靠猜 | `schema_migrations` |
| 版本单调递增 | 按序执行，每版一次 | `MIGRATIONS` 注册表（`version` 整数） |
| 校验和 | 已应用的迁移被改动要能发现 | 迁移体源码的 sha256 |
| 只前进 | 生产不回滚，改错了补一版新的 | 引擎不提供 down，只有 `up` |
| 失败不记账 | 失败必须可见、必须能重试 | 写 `success=0`，下次启动重跑 |
| 迁移体幂等 | 中断后可重入 | MySQL DDL 非事务，只能靠重入收敛 |

## 为什么不是「每次启动查一遍列在不在」

早期实现就是后者：9 个 `_migrate_*` 函数每次启动无条件跑一遍，靠 `table_has_column` 判断要不要动手。它有两个无法回避的问题：

1. **不知道当前是哪个版本**。运维问「这个库结构旧不旧」，只能逐列去猜；
2. **失败被吞掉**。历史上这些函数的异常分支是 `except Exception: pass`，迁移失败与迁移成功在日志里长得一样，等到写库报错才发现字段缺失。

现在这两件事都有明确答案：`GET /api/db/migrations` 或 `python -m framework.database.migrate status` 直接给出当前版本与待应用清单；失败会在账本里留下 `success=0` 与错误摘要，并在启动日志里以 error 级别打出。

## 结构

```
framework/database/
  migrations.py   引擎：账本读写、校验和、加锁、按序执行、基线
  schema.py       注册表 MIGRATIONS + 建表语句 + 各版迁移体
  migrate.py      运维命令行（status / up / history / check / baseline）
sql/init.sql      全新安装的完整建表（不走迁移）
```

分工的原则是：**建表不属于迁移**。全新安装直接按 `init.sql` 建出最新结构，然后账本把这 9 版直接记为已应用（各版迁移体都是幂等的，跑一遍也是空转）。迁移只服务于「已经在跑的库怎么追上代码」。

## 新增一个字段：三处同步

这是最容易漏的地方，按顺序做，缺一不可：

1. **新装的库**：改 `sql/init.sql` 与 `sql/init_mysql55.sql` 的建表语句（两个方言文件必须同改）；
2. **已在跑的库**：在 `framework/database/schema.py` 的 `MIGRATIONS` 末尾追加一版：

```python
def _migrate_groups_tag(database):
    """v10：groups_info 增加 tag 列（分组标签）"""
    if not database.table_exists('groups_info'):
        return
    if database.table_has_column('groups_info', 'tag'):
        return
    if database.db_type == 'sqlite':
        database.execute("ALTER TABLE groups_info ADD COLUMN tag TEXT DEFAULT ''")
    else:
        database.execute(
            "ALTER TABLE groups_info ADD COLUMN tag VARCHAR(64) DEFAULT '' "
            "COMMENT '分组标签'")

MIGRATIONS = (
    # ... 已有 9 版，不要动 ...
    Migration(10, 'groups.tag', _migrate_groups_tag, 'groups_info 增加 tag 列'),
)
```

3. **幂等**：先判断「要做的事是否已存在」再动手。中断重入、重复执行都靠它兜底。

版本号用 `next_version(MIGRATIONS)` 取，**不要在中间插号**：账本按版本号记账，插号会让老库把「已经做过的事」当成待办再排一遍。

## 铁律：已发布的迁移不可变

一版迁移一旦发布（哪怕只发给了自己的生产环境），**不能再改内容**。原因是账本里存的是它的校验和：

- 老库账本记录的是旧校验和，永远匹配不上新代码；
- 而账本又说「这版已应用」，所以**不会重跑** —— 改了半天等于没改；
- 结果就是这个库的结构与新装的库悄悄分叉。

引擎的做法是发现不一致就报 error 并在状态里标 `drift`，但**不重跑**。正确修法是追加一版新的迁移把差异补回来。

```bash
python -m framework.database.migrate check   # 有漂移返回 1，适合放 CI
```

## 命令行

在项目根目录执行（默认读 `config.yaml`，可用 `--config` 指定）：

```bash
python -m framework.database.migrate status     # 当前版本 / 待应用 / 漂移
python -m framework.database.migrate up         # 应用待执行迁移
python -m framework.database.migrate history    # 账本历史（版本/名称/结果/耗时/来源）
python -m framework.database.migrate check      # 只检查，有未应用或漂移返回 1
python -m framework.database.migrate baseline --version 9   # 接管老库
```

退出码：`0` 正常，`1` 有未应用迁移 / 校验和漂移 / 迁移失败，`2` 运行环境错误。

`up` 只是把启动时本来就会做的事提前做，用于「不想重启服务也想确认结构版本」的场合。

## 接管一个没有账本的老库

正常升级不需要这一步：老库首次启动时账本为空，9 版会各跑一遍（都是幂等判断，效果是空转），然后记账。

`baseline` 用于另一种情况：库结构早已是目标状态，但你又不想让引擎去逐条确认。它只写账本、不执行迁移体：

```bash
python -m framework.database.migrate baseline --version 9
```

**前提是运维确认该库结构确实等于该版本**。基线等于断言，断错了会把缺陷永久记账掩盖掉。基线行不参与校验和漂移判定（接管老库时源码对不上是常态）。

## 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/db/migrations` | 登录管理员 | 当前版本、待应用、漂移、历史 |
| POST | `/api/db/migrations/up` | 超级管理员 | 立即应用待执行迁移（写审计日志） |

`status` 的 `ok` 字段在出现校验和漂移时为 `false`，可直接接监控告警。

## 失败与并发

- **单条失败不会阻塞框架启动**，但会：写 `success=0`、error 日志列出首个失败原因、停止后续迁移（后面的版本可能依赖它）、下次启动自动重试。
- **MySQL 多节点**用命名锁 `zcbot_schema_migrations` 串行化，拿不到锁的节点跳过本次迁移并报 error（它的结构可能仍是旧的，需要重启或手工 `up`）。
- **SQLite** 没有命名锁，靠进程内锁串行化；同一个 sqlite 文件被多个进程同时写本身也不在支持范围内。
- **账本表建不出来**（只读库、无 DDL 权限）时引擎退化为「不记账、照旧执行」：结构正确优先于记账，但每次启动都会重复跑迁移并留下告警。
