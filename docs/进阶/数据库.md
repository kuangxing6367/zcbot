# 数据库

签到插件要把积分落盘、封禁插件要记操作日志——只要你开始在插件里存数据，就会碰到建表、查询和事务。默认的 SQLite 零配置即可用；场景放大后再切 MySQL，上层接口不变。

ZCBOT 支持 SQLite（默认，零配置）与 MySQL，上层使用同一套接口，
插件基本不需要感知当前是哪种数据库。

选型边界：SQLite 仅适合小环境与开发环境（个人/小群、
单写多读、单文件存储）；大环境不适合 SQLite——多群、高并发、多进程
部署、长连接保活、水平扩展等场景请使用 MySQL。方言适配只解决
SQL 能不能跑，解决不了 SQLite 的并发与扩展上限。

- 数据库封装：`framework/database/db.py` 的 `Database` 类；
- SQL 方言翻译：`framework/database/dialect.py`（纯函数）；
- 自动建表/迁移：`framework/database/schema.py` + `framework/database/init_db.py` 的 `auto_init_database(db)`；
- 调试模式引擎：`framework/database/sql_sim.py` 的 `SqlSimEngine`（无数据库时本地 SQL 模拟）；
- 配置见 [配置系统](../指南/配置系统.md#数据库)。

## 存储降级兜底（数据库不可用）

数据库存储不再构成框架的硬依赖：初始化失败（缺 MySQL 驱动、连接失败、
SQLite 路径不可写等）时框架不会因此无法启动，而是自动降级为**本地 SQL 模拟引擎**
（`SqlSimEngine`，与 `database.type: debug` 同款实现，`data/db/sql/` 下 JSON
行集落盘，查询有语义且重启不丢）：

- 降级兜底仅供"数据库没了框架还能起来"，数据以本地 JSON 行集存储，性能低、无真实事务；
  正常部署请配置 SQLite 或 MySQL；
- 显式调试模式配置 `database.type: debug` 走同一套 `SqlSimEngine`（见下节），
  适合无数据库的开发/联调环境；
- 旧版 `database.type: file`（降级文件存储）**已移除**：该模式 SQL 调用一律返回空值、
  无实际持久化能力，现已不可用；若配置中仍写 `type: file`，框架启动将明确报错提示改用
  `sqlite` / `mysql` / `debug`；
- 框架通过 `framework.db_debug_mode`（True 表示调试/降级兜底模式）与 `framework.storage_mode`（sqlite/mysql/debug）感知当前后端；连接池状态可用 `ctx.db_pool_status` 查看。

## 调试模式（低性能模式 / 本地模拟 SQL）

在**没有 SQLite/MySQL 依赖**的开发、联调环境（如 CI 冒烟、最小复现、
无数据库沙箱），可通过抽象层开启调试模式：`database: { type: debug }`。

- 存储抽象层：`framework/database/storage.py` 的 `create_storage(config)`
  按 `database.type` 选后端 —— `sqlite/mysql → Database`、
  `debug → SqlSimEngine`；上层访问接口完全同构，
  插件与内核无需改动；
- 模拟引擎：`framework/database/sql_sim.py` 的 `SqlSimEngine`，在本机
  用 JSON 行集文件"假扮"数据库（`data/db/sql/<表>.json`，原子写、重启不丢），
  **查询返回符合 SQL 语义的结果**（非空值兜底）：
  - SELECT：`*` / 列 / `COUNT(*)` / `DISTINCT` / `DATE(col) AS d`、
    WHERE（`=` `<>` `!=` `>` `<` `>=` `<=` `AND` `OR` `IN` `NOT IN`
    `IS NULL` `LIKE`，支持 `%s`/`?` 参数与字面量）、`GROUP BY`、
    `ORDER BY`、`LIMIT` / `OFFSET`；
  - INSERT [IGNORE]、UPDATE（`NOW()`、`col=col+N` 自增）、DELETE、CREATE TABLE；
  - 不支持的语法（JOIN/子查询/复杂表达式/ALTER）安全兜底：查询返回 `[]`、
    写返回 `0`，绝不抛异常，保证框架可启动；
- 调试模式适合无数据库的开发/联调环境，可真实验证查询/写入逻辑；
  生产或常规部署请使用 SQLite / MySQL（性能、事务、并发能力均更强）。
  但它性能低、无真实事务与并发保证，**仅限开发调试，生产必须用 sqlite/mysql**；
- 行集内存缓冲：行集常驻内存，读写不再逐次全量解析/重写 JSON 文件；
  写入先进缓冲，按 `database.debug_flush_ms`（毫秒，默认 `1000`，`0`=逐次
  同步落盘）由后台线程合并落盘，正常关停/进程退出兜底全量落盘（进程被强杀
  最多丢最近一个刷盘间隔的写入）；外部/手工改动 JSON 文件按 mtime 自动重载；
- 框架感知：`framework.storage_mode`（`sqlite/mysql/debug`）与
  `framework.db_debug_mode`（True 表示调试模式）暴露当前后端。

```yaml
# config.yaml —— 调试模式（低性能模式：本地模拟 SQL）
database:
  type: debug         # 无需任何数据库依赖，行集落盘 data/db/sql/
  debug_flush_ms: 1000  # 内存缓冲刷盘间隔（毫秒），0 = 每次写同步落盘
```

## 自动初始化

框架启动时根据 `config.yaml → database` 建立连接并自动建表：

- SQLite：按 `database.path`（默认 `data/zcbot.db`）创建文件库；
- MySQL：自动探测版本与字符集，适配 DDL 后建库建表。

插件不要自己去改框架表结构；自己的业务表用 `ctx.create_table()` 创建。

建表之后的**字段/索引演进**走版本化迁移（账本表 `schema_migrations`，只执行未应用过的版本，失败会记账并在下次启动重试）：

- 新增字段要三处同步：`sql/init.sql` + `sql/init_mysql55.sql` + `MIGRATIONS` 里追加一版；
- 已发布的迁移不可改（账本有校验和，改了只会报漂移、不会重跑）；
- 详见 [数据库迁移](/进阶/数据库迁移)。

## 插件建表：统一写 MySQL 方言

```python
def register(ctx):
    ctx.create_table("""
        CREATE TABLE IF NOT EXISTS my_data (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            user_id INTEGER NOT NULL,
            score INTEGER DEFAULT 0,
            memo TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
```

框架自动完成方言适配，插件无需判断数据库类型：

- SQLite：`AUTO_INCREMENT → AUTOINCREMENT`、`ENUM → TEXT`、移除不支持的内联 INDEX 等；
- MySQL：`AUTOINCREMENT → AUTO_INCREMENT`，对长文本列上的索引自动改成
  前缀索引 `col(191)`，规避 MySQL 的 1170/1064 错误。

建议在 `register(ctx)` 里建表（幂等，`IF NOT EXISTS`），每次注册都会确保表存在。

## 查询接口

### 同步

```python
rows = ctx.db_query("SELECT * FROM users WHERE group_id=%s", (group_id,))     # list[dict]
row  = ctx.db_query_one("SELECT * FROM users WHERE user_id=%s", (user_id,))  # dict / None
n    = ctx.db_execute("UPDATE users SET score=score+%s WHERE id=%s", (1, id_))  # 受影响行数
new_id = ctx.db_insert("INSERT INTO logs (msg) VALUES (%s)", ("hello",))     # 自增 ID
ctx.db_execute_many("INSERT INTO t (v) VALUES (%s)", [(1,), (2,)])           # 批量
```

### 异步（async handler 推荐）

异步方法在数据库专用线程池执行，DB 繁忙也不会卡住消息事件循环：

```python
rows = await ctx.db_query_async(sql, params)
row  = await ctx.db_query_one_async(sql, params)
n    = await ctx.db_execute_async(sql, params)
new_id = await ctx.db_insert_async(sql, params)
await ctx.db_execute_many_async(sql, params_list)
```

查询结果统一为 `dict`（单条）或 `list[dict]`（多条），列名即键。

## 占位符：统一用 `%s`

无论 SQLite 还是 MySQL，插件 SQL 一律写 `%s` 占位符，框架在 SQLite 下
自动转换成 `?`。不要拼接字符串，避免 SQL 注入与方言问题：

```python
# 正确：参数化
ctx.db_execute("UPDATE t SET v=%s WHERE id=%s", (v, id_))
# 错误：字符串拼接
ctx.db_execute(f"UPDATE t SET v={v} WHERE id={id_}")
```

## 事务

多条必须一起成功/失败的写操作，用 `db_connection()` 取连接手动提交/回滚。
连接池模式下 `close()` 是归还连接，不是断开：

```python
conn = ctx.db_connection()
try:
    cur = conn.cursor()
    cur.execute("UPDATE account SET balance=balance-%s WHERE id=%s", (100, from_id))
    cur.execute("UPDATE account SET balance=balance+%s WHERE id=%s", (100, to_id))
    conn.commit()
except Exception:
    conn.rollback()
    raise
finally:
    cur.close()
    conn.close()
```

## 连接池状态

```python
ctx.db_pool_status     # dict：连接池占用/空闲等状态，便于排障
```

## 切换到 MySQL 的完整写法

把 `config.yaml` 的 `database` 段改成下面这样（**所有键与 `type` 平级**）：

```yaml
database:
  type: mysql
  host: 127.0.0.1
  port: 3306
  user: zcbot
  password: "your-password"    # 数字密码请加引号
  database: zcbot              # 库名，需提前建好
  charset: utf8mb4
  pool_size: 10                # 连接池上限
  pool_wait_timeout: 30        # 池满时最多等多久（秒）
```

> 库和账号要先建好，框架只负责建表：
> ```sql
> CREATE DATABASE zcbot DEFAULT CHARSET utf8mb4;
> CREATE USER 'zcbot'@'127.0.0.1' IDENTIFIED BY 'your-password';
> GRANT ALL PRIVILEGES ON zcbot.* TO 'zcbot'@'127.0.0.1';
> FLUSH PRIVILEGES;
> ```

**三种常见写错，症状都是启动卡住而不是报配置错**：

```yaml
# ✗ 错 1：整段写成单行 flow mapping，粘贴到 database: 下面就成了嵌套
database:
  database: { type: mysql, host: 127.0.0.1, ... }

# ✗ 错 2：多嵌一层 mysql:
database:
  type: mysql
  mysql: { host: 127.0.0.1, ... }

# ✓ 对：平铺，与 type 同级
database:
  type: mysql
  host: 127.0.0.1
```

写错时框架会直接指出具体键名（如「database.host 应为字符串，实际是 dict」），
不会再把一次参数错误重试成 30 秒假死。

**权限说明**：迁移前的备份会尝试读 binlog 位点，需要 `REPLICATION CLIENT`
（或 MySQL 8 的 `BACKUP_ADMIN`）权限。普通业务账号没有该权限时会打印
`v2 执行前备份未完成 — 无法读取 binlog 位点` 并继续执行迁移——请自行确认
已有实例级备份，或给账号补上该权限。

## SQLite vs MySQL 对比

| 特性 | SQLite | MySQL |
|------|--------|-------|
| 配置 | 零配置，单文件 | 需 host/port/user/password/database |
| 并发 | 单写多读，适合轻量场景 | 支持高并发 |
| 占位符 | 插件写 `%s`，运行时转 `?` | 原生 `%s` |
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `INT ... AUTO_INCREMENT PRIMARY KEY` |
| 适合规模 | 仅小环境与开发环境（个人/小群、本地调试） | 大环境（多群、高并发、多进程部署） |

结论照抄即可：

- 本地开发、个人号、小群试点 → `database.type: sqlite`（默认，零配置）；
- 生产上线、多群、消息量大、双进程/多 worker → `database.type: mysql`，
  不要用 SQLite 顶大环境（写锁、单文件、无网络拓扑，扩容到头就是换库）。
- 从 SQLite 迁到 MySQL：改 `config.yaml` 后重启，框架会按 `sql/init.sql`
  自动建表；业务数据需自行导出导入（结构为 MySQL 方言，双方言通用）。

## 自动备份

SQLite 有一个常驻的备份线程（默认每 6 小时一次），**不需要额外装任何东西**。
MySQL 不走这一层：`mysqldump` 会长时间锁表、体积不可控，请用实例级备份或
binlog 恢复点（迁移前的 binlog 位点记录仍然保留）。

```yaml
database:
  migrations:
    keep_backups: 2              # 迁移前备份保留份数（与自动备份统一 2 份）
  backup:
    enabled: true
    interval_hours: 6            # 每 6 小时一次
    initial_delay_minutes: 5     # 启动后等 5 分钟再跑首次；0 = 启动不跑
    keep: 2                      # 最多保留 2 份
    compress: true               # 超过阈值就打包 zip
    compress_threshold_mb: 100   # 「默认不大于 100MB」：超了就压
    compress_level: 1            # 1 档：压缩时尽量不抢 CPU
    refuse_above_mb: 100         # 压缩后仍超 100MB 才暂停备份并提示
    allow_large: false           # true = 无视上限（确认库体积正常后再开）
    min_free_after_mb: 0.5       # 空间探测写到只剩 512KB 就停手并清理
    headroom_ratio: 1.10         # 预留空间 = 库体积 × 该系数
    probe_max_mb: 4096           # 探测硬上限，防止算出天文数字时写爆磁盘
    verify: true                 # 写完读回复核，过了才转正
```

备份落在库文件同级的 `backups/`，文件名 `zcbot-backup-<时间>-<来源>.zip`；
迁移前备份是 `zcbot-schema-*`，两套靠前缀分开数份数。**每个阈值都能改**。

### 一次备份做什么

1. **估算 + 空间判定**：需要 `库体积 × headroom_ratio`。够就直接跑。
2. **不够则弹性探测**：有些存储（云盘薄 provisioning、配额、overlay 上层）
   报出来的可用空间是假的，只能真写一遍才知道。探测会按需写入，**一旦可用
   空间降到 `min_free_after_mb`（默认 512KB）立刻停手并删除探针文件**——
   不是把磁盘填满。填满会让正在跑的数据库/日志写不进去，那比没有备份更糟。
   判定为「写不下」时直接中止，日志里写明原因与实写字节数。
3. **快照**：`VACUUM INTO` 到 `.part`（在线快照，不受 WAL 影响）；不支持时
   退化为文件复制并告警。
4. **压缩**：超过 `compress_threshold_mb` 才打包 zip，分块写并周期性让出
   CPU（`compress_level: 1`），不卡事件处理。`compress: false` 时整段跳过。
5. **体积上限**：**压缩之后**仍超过 `refuse_above_mb` 才**暂停备份**并提示。
   顺序不能反——先判上限的话，超过 100MB 的库根本没机会被压下来，压缩分支
   永远走不到。库突然从几 MB 涨到几百 MB 通常意味着出了事（日志表爆炸、
   循环写入），这时候悄悄备份反而是掩盖问题。确认正常后调大上限，或临时
   `allow_large: true`。压缩失败时按**原始体积**判上限，不假装压过。
6. **校验后转正**：先对 `.part` 读回校验（zip 走 CRC、db 走 `quick_check`），
   通过才改名成正式文件。有些环境写文件会「报成功但内容不对」，不校验就等于
   把坏文件当备份用。
7. **轮转**：只留最近 `keep` 份。

> 老配置里的 `compress_threshold_kb`（单位 KB，当年把 100MB 读错了）仍然认，
> 会按 KB ÷ 1024 换算成 MB 生效并打一条 warning。新配置请直接用
> `compress_threshold_mb`。

### 看状态 / 手动触发

- WebUI：`GET /api/db-backup` 看上次结果、现有备份、生效配置；
- 手动跑一次：`POST /api/db-backup/run`（超管，写审计）；
- 改阈值：`POST /api/db-backup/config`（超管），会写回 `config.yaml` 并即时生效；
- CLI：直接改 `config.yaml` 后重启，效果一样。

> `state.json` 记着上次结果，进程重启后仍能在 WebUI 看到——不然「上次备份
> 失败了」这条信息会随着重启一起消失。

## 损坏自愈

SQLite 在启动建表、查询、写入时抛出明确的损坏信号（`SQLITE_CORRUPT`、
`SQLITE_NOTADB`、`database disk image is malformed`、`file is not a database`
等），就会进入应急流程。

**只有损坏才进恢复**。判定以 SQLite 官方 result codes 为准，且结果码优先于
消息文本：下面这些虽是数据库错误，但一律**不算损坏**，由 `_emergency_recover`
直接交回调用方（查询/写入照常向上抛，调用方自行处理）：

| 错误 | 结果码 | 为什么不算损坏 |
|---|---|---|
| disk I/O error / 磁盘满 / 短读 | `SQLITE_IOERR`、`SQLITE_FULL` | 存储或系统 I/O 问题，文件内容没被判为畸形 |
| 只读 | `SQLITE_READONLY` | 挂载 / 文件只读，写入被拒 |
| 锁冲突 | `SQLITE_BUSY`、`SQLITE_LOCKED` | 并发写入，等锁即可 |
| 缺表 | `SQLITE_ERROR`（`no such table`） | SQL 层对象不存在，库文件本身完好 |
| 权限不足 | `SQLITE_PERM`、`SQLITE_AUTH` | 访问模式 / authorizer 拒绝 |
| 约束冲突、内存不足、打不开 | `SQLITE_CONSTRAINT`、`SQLITE_NOMEM`、`SQLITE_CANTOPEN` | 运行期错误，与文件损坏无关 |

损坏判定支持 `SQLITE_CORRUPT` 家族的全部扩展码（`_VTAB` / `_INDEX` /
`_SEQUENCE`）；SQLite 默认不启用扩展码、Python 的 `sqlite_errorname` 给的也是
主码，所以用主码前缀匹配即可全覆盖。只在拿不到结果码时（老 Python 或自定义
异常）才退回消息文本的官方精确短语，且不放宽到裸 `malformed` 一类宽泛词。

只读、锁冲突、磁盘满、SQL 写错都不触发损坏流程，不会误把可恢复的运行时
故障交给恢复逻辑，也不会因此把新数据悄悄写到降级库里。

### 流程

1. **先走标准备份流程**：恢复前快照直接调用自动备份那一套，空间探测、
   `.part` 写盘、读回复核、压缩、轮转全部照走，产物是
   `backups/zcbot-backup-<时间>-recovery.*`。不会用裸复制绕过这些闸门——
   否则库一大或空间不足，恢复流程自己先把磁盘写满。
   **备份没成功就停止恢复**，不在没有可靠快照的情况下改动原库。
2. **再尝试恢复**：所有操作都在临时副本上做，原库不会被半成品覆盖。
   三套手段按固定顺序试：先单独，再两两，最后六种三排列，共 12 种组合：

   | 手段 | 做法 | 限制 |
   |---|---|---|
   | A `reindex` | `REINDEX` 重建索引 | 只解决索引类损坏 |
   | B `vacuum_into` | `VACUUM INTO` 重建整库 | 库文件还得能读 |
   | C `recover_cli` | `sqlite3 <库> .recover` 导出 SQL 再重建 | 需要外部 `sqlite3` 命令；可用 `ZCBOT_SQLITE3_CLI` 指定路径 |

   一种组合内部前一步的产物交给后一步，所以 A+B、A+B+C 这类组合才有意义。
   每一步都会 `PRAGMA quick_check(1)` 复核，通过才停。
3. **转正**：成功后原库留一份 `.corrupt-<时间>`，恢复产物原子替换到原路径。
   全部失败时原库不动，备份和日志都保留。
4. **退出并计入崩溃守卫**：无论修没修好，框架都以退出码 **1** 结束，
   退出前把处置指引写进 `error.log`（路径取 `framework.crash.path`，默认项目
   根目录的 `error.log`），日志先 flush 再退出。这份日志同时是崩溃次数来源，
   由 `framework/crash_guard.py` 轮转 `.1..N`，不需要额外哨兵文件。
   恢复过程的逐次尝试另记在 `data/logs/error.log`，每行一条 JSON，含环境事实。

> 恢复结果不能当成数据完整。打捞可能丢行、把已删除内容带回来、改掉字段
> 类型或破坏约束。这句话会同时写进上面两份日志，日志第一行就说清发生了什么、
> 该怎么处理，不把一堆 traceback 直接糊给运维看。

### 退出后再次启动：交给原生崩溃计数

检测损坏 → 恢复 → 写 `error.log` → 退出，这一整条刻意走框架的**原生崩溃链**。
守护脚本（systemd / pm2）把进程拉起时，启动入口在任何插件和数据库初始化之前
先数 `error.log` 及其轮转副本：

- **未到 `framework.crash.max_restarts`（默认 5）**：照常启动。若库仍有问题，
  再撞损坏、再写一份日志、再退出，计数继续累加。
- **达到上限且 `framework.crash.safe_mode: true`（默认）**：进程挂着不动，
  不加载插件、不写库，让 `Type=simple` 的守护脚本以为已经启动、停止反复拉起。
  这是刻意设计，不是卡死。
- **达到上限且 `safe_mode: false`**：直接打印明确指引后退出，不挂起。

这样即便没人盯着告警，也不会出现「守护脚本拉起后，框架假装无事、继续往
可能已经损坏的库里写」的情况。`framework.crash.enabled: false` 会连这道门
一起关掉，只适合明确知道后果的场景；数据库损坏时不要用这个配置来绕过检查。

人工处置顺序：核对前面那份标准备份 → 确认是否需要回滚 → 删除 `error.log`
及其 `.1/.2...` 轮转副本 → 重启。新进程正常启动后会自行清零计数。

> 旧版本曾用 `data/db-recovery.exit` 哨兵提醒「库被自动恢复过」，现已移除。
> 计数、轮转、安全模式和外部告警全部复用崩溃守卫，少一份要解释的状态文件。

### 损坏时仍能登录 WebUI：应急管理员入口

上面这条链解决「启动期撞到明确损坏」的情况。还有一种更常见的故障：框架
能起来、WebUI 也能打开，但 `admin_users` 这张表坏了 / 丢了 / 查询就报错，
于是登录页永远进不去，人就被挡在门外，连恢复和备份页面都点不到。

为此提供一份**不依赖数据库**的应急管理员，配置在 `data/admin_emergency.yaml`：

- **首次启动自动生成**：随机用户名（`emerg_` 开头）+ 随机强密码，密码只在
  控制台打印一次，文件里只存 bcrypt 哈希和一个 token 签名密钥，权限 0600。
  忘记密码可执行 `python -m framework.api.emergency_admin --reset` 重新生成，
  旧 token 随即全部失效。明文不落盘、不进日志、不入库。
- **只在 DB 侧认证失败时兜底**：正常管理员照旧走 `admin_users`；仅当登录查询
  抛异常或账号不存在，且输入的用户名正好命中应急账号时，才校验应急密码。
  它不是常驻的第二个超管，DB 正常时这个账号照常「查无此人」。
- **权限为 super，但带应急标记**：应急身份带 `emergency: true`，能进数据库 /
  备份等页面做修复；每次应急登录和操作写 `data/logs/emergency_admin.log`
  独立审计（审计表此刻多半也写不进去）。
- **token 自包含**：应急 token 形如 `eme1.<载荷>.<签名>`，校验只验 HMAC 签名、
  有效期和用户名，全程不查库——否则库坏了照样过不了鉴权。有效期取
  `web.session_timeout`。篡改、过期、用户名不匹配一律拒绝。

> 这是救急通道，不是日常入口。恢复完成、核对数据无误后，建议执行
> `--reset` 换掉凭据并妥善保存新密码；不要把明文密码记进工单或聊天记录。
> 本入口只覆盖「框架已启动、WebUI 可访问、DB 认证链路不可用」的场景。
> 若框架在启动期就因损坏退出（走上面的自愈链），WebUI 本就不在线，
> 此时应看 `error.log` 按崩溃计数与安全模式的口径处置。

## 字段元信息系统

框架为业务表维护字段描述等元信息，配套提供（通过 ctx/框架能力）：

- 描述字段、更新字段描述、列出全表字段描述；
- 群级动态列等高级能力。

插件自定义表只要遵循统一建表入口，即可被这些能力识别。

## 实践建议

1. 表名加插件前缀（如 `sign_records`），避免不同插件撞表；
2. `async def` handler 里一律用 `*_async` 接口；
3. 建表 DDL 保持幂等（`IF NOT EXISTS`），在 `register(ctx)` 调用；
4. 高频写库考虑批量接口 `db_execute_many`；
5. 用户可改的配置走 `_conf_schema.json` + `ctx.get_config`，不要自己建配置表。
