# 可靠性与限流

入站事件进入内核之前，会先过一道守卫：**重放去重**与**消息流限流**。它解决的不是业务逻辑问题，而是生产环境里最容易先把机器人拖垮的两类问题。

## 为什么放在内核层

成熟 IM 框架（OneBot 生态、Koishi、各类生产级 bot）的共识是：机器人第一次事故通常不是命令写错了，而是

- **断线重连后同一批消息被重推**，机器人对同一条消息回复了两遍，甚至重复扣费、重复建单；
- **某个群刷屏或被脚本打**，事件瞬间堆满内存缓冲，进程 OOM 或被平台判为滥用。

这两件事都属于「基础设施先建」的范畴——等出事再补，往往要停机改架构。所以守卫放在 `framework/messaging/inbound_guard.py`，由内核在 `dispatch_event` 中调用，插件无需感知。

## 位置：归一化之后、入队之前

```
适配器 → dispatch_event()
           ├─ 1. 事件契约补齐（normalize_event）
           ├─ 2. 入站守卫（去重 + 限流）   ← 在这里
           ├─ 3. event.before_dispatch 扩展点
           └─ 4. 进入分层缓冲（L1 → L2 → L3）→ worker
```

放在第 2 步而不是 worker 里，有两个原因：

1. 被拦掉的事件**不占用缓冲槽**，限流才真的能保护内存；
2. 去重依据是 `message_id`，归一化之后才有稳定值。

守卫自身抛异常时**放行**事件——宁可漏拦，也不能让消息凭空消失。

## 配置

```yaml
reliability:
  dedup_window: 300            # 去重窗口（秒），0=禁用
  rate_limit:
    enabled: false             # 默认关闭
    window: 60
    global_per_min: 0          # 0=不限
    group_per_min: 0
    user_per_min: 0
    action: skip               # skip | notify
    notify_text: "消息过于频繁，请稍后再试。"
```

默认值是有意为之：

- **去重默认开**（300 秒）。它只拦「同一接入端 + 同一 `message_id`」的重复，正常使用几乎不可能误伤，属于纯收益。
- **限流默认关**。阈值带业务属性——大群和小群、私聊和群聊的合理上限差一个数量级，框架没有资格替部署方拍板。

## 去重语义

- 只对 `post_type == 'message'` 生效。`notice` / `request` / `meta_event` 本身幂等，不去重（否则会漏掉真实的重复通知）。
- 键是 `(bot_name, message_id)`。多接入端同时在线时，不同 bot 的 `message_id` 可能撞号，必须区分来源。
- 内存有硬上限（2 万条）。超限时先清过期，仍超限再淘汰最早插入的条目，不会无限增长。

## 限流语义

三级滑动窗口，从小到大依次判定：`global` → `group` → `user`；命中任一级即丢弃。

- `global_per_min`：整机上限，防全局打爆；
- `group_per_min`：单群上限，跨用户累计（刷屏通常是多人一起）；
- `user_per_min`：单用户上限，跨群累计。

`action`：

| 值 | 行为 |
|---|---|
| `skip` | 静默丢弃，不回复 |
| `notify` | 丢弃，并在同一窗口内至多回复一条提示（避免提示本身变成刷屏源） |

提示走 `reply_text()`，由当前接入端翻译成本平台的消息格式。

## 观测

- 去重丢弃打 `debug`：重放属于正常现象，不该刷生产日志；
- 限流丢弃打 `warning`，含 `bot` 与命中层级（`rate_limit:user` 等），便于排查「消息为什么没回」。

需要长期观察时，配合 [可观测性与运维接口](./可观测性与运维.md) 的 `/metrics` 做日志聚合。

## 已知边界

1. **去重是内存态**：进程重启后窗口清空，重启瞬间的重放拦不住（OneBot 侧一般不会跨进程重推同一批）。
2. **只在单进程内生效**：双核心架构下 core 与 host 各自持有一份守卫，`message_id` 在三方之间有碰撞风险时需按 `bot_name` 区分，框架已按此取键。
3. **没有出站节流**：本守卫只控入站。插件自己高频发消息（如批量推送）仍需自律；平台侧的发送频率限制不在此模块覆盖范围。

## 测试

`tests/test_inbound_guard.py`（13 组）覆盖：重放拦截、窗口过期、`notice` 不去重、多接入端区分、三级限流、`notify` 每窗口只提示一次、容量淘汰、`sweep()` 释放、异常字段健壮性，以及**走真实 `dispatch_event` 的接线验证**（确认守卫确实在入队前执行）。
