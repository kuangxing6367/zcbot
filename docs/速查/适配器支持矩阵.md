# 适配器支持矩阵（接入端清单与缺口）

> 术语说明：「企业类接入端」指企业微信、钉钉、飞书这类办公 IM 平台；文中「适配器」与「接入端」同义。
>
> 本文只做现状清单与缺口分析，**不新增适配器的完整实现**。是否新增排在需求确认之后。
>
> 核查范围：`framework/messaging/adapter_registry.py`、`framework/messaging/contract.py`、
> `framework/messaging/segments.py`、`framework/messaging/protocol.py`、`core_plugins/` 下全部
> `protocol_adapter` 注册点。`framework/ipc` 通信层已搁置，不计入。

---

## 1. 先分清三层，别把「规范能表达」当成「已经能接入」

| 层 | 位置 | 实际作用 |
|---|---|---|
| 身份注册表 | `framework/messaging/adapter_registry.py` | 只做 `adapter_key ↔ uuid` 映射与身份命名空间，不枚举能力、不判断支持与否 |
| 契约与规范段 | `framework/messaging/contract.py`、`framework/messaging/segments.py` | 定义 4 类事件、13 类规范通知、2 类请求、能力常量 `CAP_*` 与全部规范段；只是「能表达」 |
| 适配器实现 | `core_plugins/<name>/main.py` | 真正继承 `ProtocolAdapter` 并调用 `services.register('protocol_adapter', ...)` 的接入端；8 个 |

`contract.py:119` 的 `CAP_CARD = 'card'  # 交互卡片（飞书/钉钉/企微）` 与
`segments.py:56-58` 提到飞书/钉钉/企微，都只是规范层命名注释。全仓检索这些平台名
只命中 7 处注释与旧文档，**没有任何对应插件、注册点、配置项或 API 实现**。

判定口径：

- **已支持**：四类规范事件齐备，有明确的入站归一化与出站翻译，发送/动作实现较完整。
- **部分支持**：适配器存在，但事件只覆盖一部分，或出站媒体/动作受限，或只是透传桥、入站注入端。
- **缺失**：只有规范层命名或文档注释，没有适配器实现。

## 3. 规范层现状与别名陷阱

- 事件类型（`contract.py:30-34`）：`message`、`notice`、`request`、`meta_event`。
- 规范通知（`contract.py:81-86`）13 类：成员增减、群封禁、群管理、群上传、群精华、消息撤回、戳一戳、好友增删、按钮交互、回调查询等。
- 请求类型（`contract.py:89`）：`friend`、`group`。
- 规范段（`segments.py:35-70`）：除常用 text/at/image/voice/video/file 外，已有
  `card`、`post`、`button`、`reaction`、`quote`、`embed`、`ephemeral` 等富类型。
- 能力常量（`contract.py:95-134`）：`CAP_CARD`、`CAP_POST`、`CAP_BUTTON`、`CAP_MARKDOWN`、
  `CAP_QUOTE`、`CAP_REACT`、`CAP_EDIT`、`CAP_PIN`、`CAP_THREAD` 等。

必须注意的别名（`segments.py:99-143`）：

| 写法 | 归一后 | 影响 |
|---|---|---|
| `card` | `json` | 历史兼容名，真正的卡片要用 `interactive` / `template` / `interactive_card` |
| `quote` | `reply` | 话题引用要用 `thread` / `topic` / `quote_message` |
| `animation` | `video` | 动图不会落到独立 `animation` 段 |
| `audio` | `voice` | 音频文件折叠进语音 |
| `record` | `voice` | OneBot 写法兼容 |

因此「规范层有 card/post/button」不能推出「飞书/钉钉/企微已接入」。

## 4. 三个企业类缺口：最小接入面与规范段够不够

### 4.1 企业微信 / 企微

| 面 | 最小需要 | 现有规范段是否够 |
|---|---|---|
| 事件类型 | `message`（text/image/voice/video/file/location/link）；`notice`（成员进群、退群、名片点击、模板卡片按钮回调）；`request` 暂不需要 | 事件四类齐备；回调要映射到 `notice.interaction` / `notice.callback_query` |
| 消息段映射 | text→`text`；image/voice/video/file→同名媒体段；location→`location`；link→`share`；模板卡片→`card`；卡片按钮→`button` | 基本够用，但 `card` 的 data 需要约定 `card_type`、`callback_key`、`card_action`；`media_id` 引用要进 `MEDIA_DATA_KEYS` |
| 媒体获取 | 自建应用 `access_token` → 素材/临时素材下载 API，拿到 `media_id` 对应的字节；群机器人 webhook 只发不收 | 规范段已能承载 `file_id` 式引用，`media_io.download()` 返回 `needs_adapter`，需适配器实现换取真实地址 |
| 发送动作 | 应用消息：text/image/voice/video/file/textcard/markdown/template_card；群机器人 webhook：text/markdown/image/news/template_card/file | `card`/`button`/`markdown` 够表达主体；`news`/`textcard` 可映射到 `card` 或 `share`，不强制新增顶级段 |
| 鉴权 | `corp_id + corp_secret` 换 `access_token`；回调 `msg_signature + timestamp + nonce` 校验与 `EncodingAESKey` 解密；群机器人 `key` | 框架无统一鉴权抽象，由适配器各自实现，不依赖规范段 |

结论：规范段**基本够用**，缺口在实现层；建议在 `card` 的 data 约定企业微信模板卡片子结构，
并把 `media_id` 明确列入 `MEDIA_DATA_KEYS`。不需要新增顶级段；若后续要求 `news/textcard`
与交互卡片严格区分，可再评估 `SEG_ACTION_CARD`，当前不新增。

### 4.2 钉钉

| 面 | 最小需要 | 现有规范段是否够 |
|---|---|---|
| 事件类型 | Stream 模式或 HTTP 回调收群/会话消息；卡片按钮回调与入群事件映射到 `notice.interaction` / `group_member_increase` | 事件四类齐备；`request/meta_event` 首版可不覆盖 |
| 消息段映射 | text/markdown→`text`/`markdown`；image/voice/video/file→同名媒体段；`actionCard`→`card + button`；`feedLink`→`share` 或 `card` | 够用；`actionCard` 的 `buttonOrientation`、`btnJSONList`、`feedLink` 的 `imageURL` 等落在 `card`/`button` 的 data 扩展键 |
| 媒体获取 | 先拿 `access_token`，再用 `downloadMedia` / 媒体文件下载接口把 `mediaId` 换成字节；群机器人只支持发送 | `file_id` 式引用已能表达，`download()` 会返回 `needs_adapter`，需适配器实现换取真实地址 |
| 发送动作 | 群机器人 webhook：text/link/markdown/actionCard/feedLink；企业内部机器人：工作通知、群会话消息；卡片回调回应 | `text`/`markdown`/`share`/`card`/`button` 够；无需为 `feedLink` 单独开顶级段 |
| 鉴权 | 机器人 webhook `access_token` + 加签 `timestamp + sign`；企业内部应用 `appKey + appSecret` 换 token；Stream 模式凭证 | 同企业微信，鉴权在适配器内实现 |

结论：规范段**够用**，缺口在实现层；需要在 `card`/`button` 的 data 约定钉钉 actionCard
字段，并把 `mediaId` 列入 `MEDIA_DATA_KEYS`。若要求 `feedLink` 作为独立一等公民，
可评估 `SEG_FEED_LINK`，当前映射到 `share`/`card` 即可，不新增。

### 4.3 飞书

| 面 | 最小需要 | 现有规范段是否够 |
|---|---|---|
| 事件类型 | `im.message.receive_v1`→`message`；`im.message.reaction.created_v1` 等→`notice.interaction`；`im.chat.member.bot.added_v1` 等→`notice.group_member_increase`；首版可不覆盖 `request/meta_event` | 事件四类齐备；表情回应已有 `CAP_REACT`/reaction 段，回调走 notice |
| 消息段映射 | `text`→`text`；`post`→`post`；`image/file/audio/sticker`→同名媒体段或 `sticker`；`interactive`→`card`；`share_chat`→`share` | 基本够用；`post` 的多段富文本结构与 `interactive` 的 `header/elements/card_action` 需要 data 约定；`file_key` 要列入 `MEDIA_DATA_KEYS` |
| 媒体获取 | `tenant_access_token` → `im/v1/messages/:message_id/resources/:file_key?type=image/file` | `file_key` 可复用 `file_id` 字段；`download()` 的 `needs_adapter` 语义正合适 |
| 发送动作 | `im/v1/messages` 按 `receive_id_type` 发 text/post/image/file/audio/sticker/interactive；撤回、表情回应 | `post`/`card`/`sticker`/`reaction` 已有；无需新增顶级段 |
| 鉴权 | `app_id + app_secret` 换 `tenant_access_token`；事件订阅 verification token 与 encrypt key 校验解密 | 同前两家，鉴权在适配器内实现 |

结论：规范段**够用**，缺口在实现层；需要补的是 `post`、`card` 的 data 结构约定和
`file_key` 引用键，不需要新增顶级段。

需求确认前不新增适配器实现；若确认要做，建议按「先钉钉、再飞书、最后企业微信」的
顺序单独立项，每家都按上表的最小接入面交付。
