# zcbot 主线 · 16 轮代码缺陷审计（opencode 专用简报）

## 你的身份与硬约束

- 你是本仓库的**审计员**，不是开发者。
- **不要修改任何产品代码**（`framework/`、`core_plugins/`、`tests/` 一个字都不改）。
- **不要打 tag、不要发版、不要动 VERSION / CHANGELOG / pyproject.toml**。
- 只读、只查、只写你自己的报告文件。
- 每轮只把你这一轮的材料当线索，用 Grep 搜相关调用点可以，但**不要 Read 任何超过 150 行的文件**——端点不稳，读大文件会卡死整个任务。

## 本轮任务

1. 读当前目录的 `round_N.md`（N 是本轮编号），里面写着本轮范围和摘录文件名。
2. 读该轮的小摘录（约 130 行）。
3. 针对摘录覆盖的代码，找**真实存在的缺陷**，重点：
   - 一句看似无害的调用就能破坏全局/共享状态（参考已修的 `db.close()` 关池、Guard fail-open）；
   - 资源泄漏（连接/句柄/线程/队列）、锁误用、生命周期错配；
   - 异常吞噬导致的状态不一致、静默失败；
   - 并发/竞态、边界输入、类型误用。
4. 跑 ruff 两道门禁（在仓库根目录执行），确认本轮范围没有风格/未定义名问题：
   ```
   ruff check --isolated --select F821 .
   ruff check --select UP009,I001,UP032,F541,PIE790,RET501,PLR1711,RUF022,FURB167,UP006,UP045,RUF100 .
   ```
5. 把发现写到本轮报告文件 `audit_round_N.md`（路径见 round_N.md）。

## 报告格式（每轮固定）

```markdown
# 第 N 轮审计：<模块名>

范围：<文件/行段>

## 发现

### D-N-1 <一句话标题>
- 位置：`文件:行号`
- 触发：怎么触发
- 影响：会造成什么（能否自愈、有无告警）
- 证据：引用关键代码 3-5 行，或描述你实跑验证的结果
- 建议：怎么改（只写建议，不要动手改）

（没有发现就写「本轮未发现可确认的缺陷，已检查的边界：…」，不许编造问题）

## ruff 结果
两道门禁的实际输出（原样贴关键行）

## 本轮结论
一句话：发现 N 个问题 / 无问题。
```

## 收工

写完全部报告后，回答一句 `ROUND_N_DONE` 即可。不要继续下一轮——下一轮由外部调度。
